# Deploying to Render and Supabase

The API runs on Render from the [Dockerfile](../Dockerfile). Postgres and the product images live in one Supabase project. This is the managed alternative to the single-server setup in [README.md](README.md).

## 1. Supabase

1. Create a project at supabase.com. Pick the **Mumbai (ap-south-1)** region and save the database password somewhere safe.
2. **Storage → New bucket:** name it `product-images` and turn on **Public bucket**. Images are served straight from here, because Render's disk is wiped on every deploy.
3. **Connect → Session pooler:** copy the connection string. Use the session pooler, not the direct connection: the direct one is IPv6-only, and Render can't reach it.
4. **Project Settings → API Keys:** copy the **Project URL** (`https://<ref>.supabase.co`) and a secret key: either the new **secret** key (`sb_secret_…`) or the legacy **service_role** key (`eyJ…`), both work. Never use the publishable or anon key. The secret key bypasses all access rules, so it only ever goes into Render's settings, never into the apps.

## 2. Create the tables

Run the migrations from your laptop. Render's free plan has no pre-deploy step, and the production image doesn't include the Prisma CLI.

```sh
cd back-end
DATABASE_URL="postgresql://postgres.<ref>:<password>@aws-0-ap-south-1.pooler.supabase.com:5432/postgres?sslmode=require" npm run db:deploy
```

In PowerShell, set it first: `$env:DATABASE_URL="..."; npm run db:deploy`.

Run this again whenever a new migration is added, **before** pushing the code that uses it. Don't run `db:seed` here: it creates demo users and a default admin password.

## 3. Render

1. Push the back-end repo to GitHub.
2. In Render: **New → Blueprint**, pick the repo. Render reads [render.yaml](../render.yaml) and asks for the three secret values listed in [.env.render.example](../.env.render.example):
   - `DATABASE_URL`: the session pooler string ending in `?uselibpqcompat=true&sslmode=require`. (The runtime driver needs `uselibpqcompat=true` to accept Supabase's certificate; the laptop migration in step 2 doesn't.)
   - `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`.
   `JWT_SECRET` and `ADMIN_REGISTRATION_SECRET` are generated by Render.
3. Wait for the deploy, then check `https://<service>.onrender.com/api/v1/health` returns `"status":"UP"`.

## 4. First admin

Copy `ADMIN_REGISTRATION_SECRET` from the service's **Environment** tab, then:

```sh
curl -X POST https://<service>.onrender.com/api/v1/auth/admin/register \
  -H 'Content-Type: application/json' \
  -H 'x-admin-registration-secret: <ADMIN_REGISTRATION_SECRET>' \
  -d '{"name":"...","email":"...","password":"..."}'
```

Afterwards, change `ADMIN_REGISTRATION_SECRET` to a new random value (`openssl rand -base64 48`) so the link can't be reused. Sign in to the admin site and add the categories.

## 5. Point the apps at it

- **Mobile:** set `EXPO_PUBLIC_API_ORIGIN` in [mobile/eas.json](../../mobile/eas.json) to `https://<service>.onrender.com` for the build profiles, or in `mobile/.env.local` for Expo Go.
- **Admin site:** run it with `VITE_API_ORIGIN=https://<service>.onrender.com`. If you host it somewhere, add its address to `CORS_ORIGINS` in Render.

## Day to day

- **Update:** push to the repo; Render redeploys automatically.
- **Logs and tester OTPs:** the service's **Logs** tab. While `ALLOW_CONSOLE_SMS=true`, OTP codes show up there.
- **Backups:** Supabase's free plan has no downloadable backups. Before risky changes, take one yourself: `pg_dump "<session pooler url>" -Fc -f backup.dump`.

## Free plan limits

- Render free services **sleep after 15 minutes** without requests; the next request takes about a minute while it wakes. A paid instance stays awake.
- Supabase free projects **pause after a week** without activity; resume them from the dashboard.
- Both are fine for testing; move to paid plans before real customers use it.
